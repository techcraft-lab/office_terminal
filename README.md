# office_terminal

退室時の点検と社員の在席状況を記録する、Ubuntu Server 向けの学習用Webアプリケーションです。Python、FastAPI、SQLiteを使い、日本語の画面を提供します。依存関係は [`uv`](https://docs.astral.sh/uv/) で管理します。

## プロジェクトの背景

日々の点検や在席確認を手作業で行う業務を改善するとともに、若手エンジニアが実際の課題を題材に、Webアプリケーション、データベース、テスト、運用上の注意点を学べるプロジェクトとして公開します。利用者がコードを読み、自由に改造・機能追加することを想定しています。

## 実装済みの機能

- 退室点検の入力・保存と、点検下書きのブラウザー保存・再開
- 出社・離席・戻り・退勤の記録
- 点検履歴・在席履歴と月間カレンダー
- 気象庁の公開予報データを使った天気表示
- CSVによる社員情報の登録・更新
- 任意設定のバックアップ・復元（保存先未設定時は無効）

## 未実装の機能・拡張アイデア

以下は今後の拡張案であり、現在の実装には含まれません。

- ICカードによる出退勤
- 顔認証による本人確認
- 社員情報をブラウザーから管理するWeb画面
- 人感センサーとの連携
- タッチ端末やスマートフォンに合わせたUI改善

## 動作環境とセットアップ

- Ubuntu Server（開発・テストは他のOSでも可能）
- Python 3.11
- `uv`

```bash
uv sync --locked
uv run python -m office_terminal.cli serve
```

起動後、同じマシンのブラウザーで `http://127.0.0.1:8000/` を開きます。既定ではローカルからのみ接続できます。操作確認用の架空社員が必要な場合は、アプリを停止してから `uv run python -m office_terminal.cli add-development-employees` を実行してください。初回起動で社員や点検記録が自動登録されることはありません。

## セキュリティ上の制約

- ログイン・権限管理・本人認証はありません。社員の選択は本人確認にならず、接続できる人は画面や記録にアクセスできます。
- インターネットへ公開しないでください。LANで使う場合も、管理者の承認とネットワーク制限を確認してください。
- 社員情報、履歴、バックアップには業務上の情報が含まれます。実データや秘密情報をサンプル・テスト・公開リポジトリに含めないでください。
- バックアップアーカイブは暗号化されません。保存先とファイルへのアクセスを制限してください。
- このプロジェクトは、認証や組織のセキュリティ要件を満たす本番システムとして保証するものではありません。

## DB保存先と開発用社員

SQLiteファイルの標準保存先は `~/.local/share/office_terminal/office_terminal.db` です。起動時にテーブルを安全に初期化しますが、社員や点検記録を自動登録・削除することはありません。

テストや別の開発環境では `OFFICE_TERMINAL_DB_PATH` で保存先を変更できます。

```bash
export OFFICE_TERMINAL_DB_PATH=/tmp/office_terminal-dev.db
```

社員情報はCSVをエディタで編集し、停止中の管理CLIからDBへ反映します。CSVはUTF-8またはUTF-8 BOM付きで、社員番号・氏名の前後空白は取り除かれます。社員番号は文字列として保持されるため、`001` の先頭ゼロも維持されます。

```csv
employee_id,display_name,is_active
001,開発用 山田,1
002,開発用 佐藤,1
003,開発用 鈴木,0
```

架空データの例は [`docs/employees.example.csv`](docs/employees.example.csv) にあります。実運用ファイルはリポジトリ外（例: `~/.local/share/office_terminal/employees.csv`）へ配置してください。CSVファイルはGitの除外対象ですが、架空の例 [`docs/employees.example.csv`](docs/employees.example.csv) だけを追跡対象にしています。社員CSVには個人情報が含まれるため、アクセスを制限し、リポジトリへ追加しないでください。

```bash
# アプリを停止してから実行
uv run python -m office_terminal.cli import-employees ~/.local/share/office_terminal/employees.csv
```

CSV全体を検証してから一括反映します。不備があれば行番号と原因を表示し、社員テーブルを変更しません。新規社員は追加され、既存社員は氏名・有効状態を更新し、CSVにない社員は変更しません。成功時は追加・更新・変更なしの件数を表示します。社員番号変更は同一人物とは判断せず、旧番号の無効化と新番号の登録で管理します。社員の有効/無効化や氏名変更は過去の点検記録に保存された氏名へ影響しません。取込は稼働ロックとバックアップ実行ロックを取得するため、アプリ・バックアップ・復元の実行中は拒否されます。

## バックアップ設定・実行（オプション／初期状態では無効）

バックアップ先は環境変数 `OFFICE_TERMINAL_BACKUP_PATH` で指定します。未設定時はバックアップ無効で、点検・履歴機能はそのまま利用できます。本番ではUSBや共有フォルダの**実際のマウントポイント**を `OFFICE_TERMINAL_BACKUP_MOUNT` に設定してください。アプリはマウントポイントが接続され、バックアップ先がその配下にあることを確認してから書き込みます。USBや共有フォルダが未接続なら同じパスにできるローカルフォルダへ保存せず、失敗日時・エラーを状態に記録し、30分間隔で再試行します。マウントやネットワーク設定、ファイアウォールは変更しません。

```bash
# 例: 管理者が事前にマウントした保存先
export OFFICE_TERMINAL_BACKUP_MOUNT=/mnt/office-backup
export OFFICE_TERMINAL_BACKUP_PATH=/mnt/office-backup/office-terminal
export OFFICE_TERMINAL_BACKUP_TIME=02:00
```

主な設定:

| 環境変数 | 説明 |
| --- | --- |
| `OFFICE_TERMINAL_BACKUP_PATH` | バックアップ保存フォルダ。未設定なら無効 |
| `OFFICE_TERMINAL_BACKUP_MOUNT` | USB/共有フォルダの必須マウントポイント。本番では設定必須 |
| `OFFICE_TERMINAL_BACKUP_ALLOW_UNMOUNTED` | `1` のときだけマウント確認を省略。開発用一時フォルダ専用 |
| `OFFICE_TERMINAL_BACKUP_TIME` | 日本時間の毎日の実行時刻。既定 `02:00` |
| `OFFICE_TERMINAL_BACKUP_RETRY_MINUTES` | 自動失敗時の再試行間隔（5〜1440分）。既定30分 |
| `OFFICE_TERMINAL_OPERATIONS_CONFIG_PATH` | 復元対象の運用設定JSON。既定 `~/.local/share/office_terminal/operations.json` |
| `OFFICE_TERMINAL_BACKUP_STATE_PATH` | 実行状態JSON。既定 `~/.local/share/office_terminal/backup-state.json` |
| `OFFICE_TERMINAL_RUNTIME_LOCK_PATH` | 稼働中復元を拒否するロックファイル。既定 `~/.local/share/office_terminal/application.lock` |

開発時は一時フォルダを明示して利用できます。本番向けの `BACKUP_MOUNT` は指定せず、マウント確認の省略を開発環境だけで使います。

```bash
mkdir -p /tmp/office-terminal-backups
export OFFICE_TERMINAL_BACKUP_PATH=/tmp/office-terminal-backups
export OFFICE_TERMINAL_BACKUP_ALLOW_UNMOUNTED=1
```

アプリ稼働中は日本時間の指定時刻に1日1回自動実行します。停止中に予定時刻を過ぎていた場合は次回起動時に1回だけ補完し、停止日数分は作りません。実行状態はアプリデータ領域に保持され、手動実行では自動予定日を変更しません。設定画面には有効/無効、実行中、最終試行・成功日時、次回予定、直近のエラーが表示されます。Web画面には実行・保存先変更・復元の操作を設けていません。

今すぐバックアップするには、アプリと同じ環境変数・ユーザーで次を実行します。

```bash
uv run python -m office_terminal.cli backup-now
```

バックアップはSQLiteの整合性スナップショットと運用設定を1つのZIPにまとめ、チェックサムとDB整合性を検証してから公開します。完成品は一意な日時付きファイル名で保存し、成功時だけ30日を超えた古いアプリ管理バックアップを整理します。直近1件は30日を過ぎても残し、保存先にある無関係なファイルと元DBは削除しません。一時ファイルは隠しファイルとして作成し、失敗時には完成バックアップ名にしません。

バックアップにはSQLite内の社員・点検記録・業務データと、バックアップ先・マウント先・実行時刻・再試行間隔など復元に必要な運用設定を含みます。保存時刻・アプリバージョン・形式バージョン・チェックサムも格納します。ソースコード、`.venv`、ログ、実行状態JSON、ブラウザ `localStorage` の点検下書きは含めません。運用設定JSONではバックアップ設定と復元世代番号だけを選択して保存し、未知の項目や認証情報はアーカイブしません。アーカイブは暗号化されず、保存先のパス自体も含むため、バックアップファイルもDBと同様にアクセス制限して管理してください。共有フォルダの認証情報など秘密情報は環境変数やOSの認証機構で別途管理し、設定JSONに書かないでください。環境変数は復元後も優先されるため、同じ設定を使うにはアプリとCLIの両方で設定してください。

復元はアプリを停止してから行います。バックアップファイル・DB・設定のパスを確認した上で、確認プロンプトに `RESTORE` と入力します。検証済みの復元元だけを受け付け、上書き前のDBと設定はそれぞれのファイルと同じ場所に `.pre-restore-...` ファイルとして退避します。

```bash
# 起動中なら先に Ctrl+C で停止
uv run python -m office_terminal.cli restore-backup /mnt/office-backup/office-terminal/office-terminal-backup-YYYYMMDDTHHMMSSffffff-xxxxxxxx.zip
# 確認後に通常どおり再起動
uv run python -m office_terminal.cli serve
```

稼働中アプリが保持するロックにより復元を拒否します。起動時に同じロックを取得できない場合は、2つ目のアプリも起動しません。復元処理は稼働ロックとバックアップ実行ロックを保持し、復元と手動・自動バックアップを排他します。アプリ停止時は実行中のバックアップが完了してから稼働ロックを解放します。

復元後は新しい復元世代番号を設定します。点検画面は表示時の世代番号を送信し、保存時にサーバー側でも現在の世代と照合します。復元前に開いた画面からの送信は保存されず、送信内容に新しい世代番号を付け直すこともありません。画面の案内に従い、古い下書きを確認して破棄した後、新しい点検を始めてください。初回運用で世代番号が未設定の場合は未設定同士を照合します。運用設定を読み込めない場合は点検を保存しません。下書きそのものはバックアップに含まれません。

点検画面には有効な社員だけが表示されます。実在社員は登録せず、操作確認用の仮社員が必要な場合に限り、次の明示的なコマンドを実行してください。

```bash
uv run python -m office_terminal.cli add-development-employees
```

これは `DEV-001` など「開発用」と表示される仮社員を登録します。点検者の選択は本人認証ではありません。

## 実機固有の起動方法（参考）

このリポジトリで案内する標準起動方法は、上記の `uv sync --locked` と `uv run python -m office_terminal.cli serve` です。`office-start` や `office-terminal-kiosk` などの独自エイリアス・スクリプトはリポジトリに含まれず、標準手順ではありません。個別に設定されたタッチ端末で使う場合は、その端末の管理者が用意した別の手順を確認してください。起動スクリプトがLAN待受を有効にする場合は、接続範囲とセキュリティを事前に確認してください。

## メニューのPC・スマホ用URLとQRコード

メニュー画面ではローカルのネットワークインターフェースからIPv4候補を取得し、LAN用URLとアプリ内で生成したQRコードを表示します。接続候補はメニューを開くたびに取得し直すため、起動後にアドレスが変わった場合も更新されます。複数ある場合はインターフェース名とIPを確認して選択してください。仮想インターフェースは候補に含まれることがありますが、有線・Wi-Fi等より後に表示します。

待受設定をアプリへ確実に渡すため、推奨起動方法はアプリCLIです。既定値はローカル限定 (`127.0.0.1:8000`) です。

```bash
# ローカル限定で起動（既定値）
uv run python -m office_terminal.cli serve

# 運用者が明示的にLAN公開する場合のみ
uv run python -m office_terminal.cli serve --host 0.0.0.0 --port 8000

# 自動判定できない場合は、確認済みのLAN側IPv4を明示可能
uv run python -m office_terminal.cli serve --host 0.0.0.0 --port 8000 --display-ip 192.0.2.10
```

上の `192.0.2.10` は説明専用のドキュメント用アドレスです。表示アドレスの明示設定はQRに使うアドレスだけを指定し、実際に到達できることを保証しません。実際に使う場合は、サーバーのLANインターフェースで確認したIPv4に置き換えてください。ローカル限定で待ち受ける場合は、PC用URL・QRコードを表示しません。

### 参考: Uvicornから直接起動する場合（標準手順ではありません）

通常はアプリCLIを使ってください。Uvicornから直接起動する場合、Uvicornのコマンドライン引数はASGIアプリから安全に判別できないため、起動設定が明確でないとメニューに「接続先を確認できません」と表示します。接続先を表示する場合は、実際の待受引数と一致する値を両方設定してください。

```bash
export OFFICE_TERMINAL_LISTEN_HOST=0.0.0.0
export OFFICE_TERMINAL_LISTEN_PORT=8000
# 説明専用アドレス。実際に使う場合は確認済みのIPv4に置き換える
export OFFICE_TERMINAL_DISPLAY_IP=192.0.2.10
uv run uvicorn office_terminal.main:app --host "$OFFICE_TERMINAL_LISTEN_HOST" --port "$OFFICE_TERMINAL_LISTEN_PORT"
```

PC・スマホはサーバーと同じ社内ネットワークへ接続して利用してください。URLとQRコードの表示は通信到達性を保証するものではありません。FW・ルーター・ネットワークの設定はこのアプリでは変更しません。ログインおよび本人認証はなく、社員選択は本人確認になりません。IPv6のみの待受や起動設定・候補IPを取得できない場合は、理由をメニューに表示してQRコードを出しません。

### 運用者が明示的に社内LANへ公開する場合

既定値は引き続き `127.0.0.1` です。社内LANから利用するときだけ、運用者がサーバーの実際のLANアドレスと対象サブネットを確認し、明示的にLANインターフェースへバインドして起動してください。アドレスやサブネットを推測して設定しないでください。

```bash
# SERVER_LAN_IP は管理者が実機で確認した値を設定する
export SERVER_LAN_IP=192.0.2.10
uv run python -m office_terminal.cli serve --host "$SERVER_LAN_IP" --port 8000
```

`192.0.2.10` は説明用アドレスです。実運用では必ず実機で確認したLAN IPに置き換えてください。同じ社内ネットワーク上のPCブラウザで開くURL例:

```text
http://SERVER_LAN_IP:8000/pc/attendees
```

LAN公開するとPC専用の出社・在席画面だけでなく、既存のTOP、点検、履歴、設定等のWeb画面も接続元から参照可能になります。このアプリにログイン・本人認証はなく、社員選択は本人確認ではありません。インターネット公開、ルーターのポート転送、SSHやファイアウォール全体の有効/無効変更は行わず、組織のネットワーク管理者の許可を得てください。

Ubuntuでufwを既に運用している場合の、対象サブネットだけからTCP 8000を許可する例です。CIDRはネットワーク管理者に確認した値を設定し、アプリ利用後は組織のルールに従って個別ルールを管理してください。ufwが無効の場合に全体を有効化する操作は行わないでください。

```bash
# OFFICE_SUBNET_CIDR はネットワーク管理者に確認したCIDRに置き換える
export OFFICE_SUBNET_CIDR=192.0.2.0/24

# 設定前の状態確認（出力を確認し、既存ルールやSSH接続に影響しないことを確認）
sudo ufw status numbered

# 対象サブネットから、このホストのTCP 8000だけを許可
sudo ufw allow from "$OFFICE_SUBNET_CIDR" to any port 8000 proto tcp

# ルールを確認。不要になった個別ルールは管理者が番号を確認して削除する
sudo ufw status numbered
```

サーバー側では待受先を確認し、PC側から到達性を確認します。ファイアウォールやネットワーク設定の変更はこの手順の利用者が管理者承認の下で行い、このアプリは変更しません。

```bash
# サーバーでTCP 8000の待受アドレスを確認
ss -ltnp | grep ':8000'

# PCから、管理者が確認したLAN IPで疎通を確認
curl --fail "http://$SERVER_LAN_IP:8000/api/attendees"
```

## VS Code Remote SSH からの確認

1. Remote SSH 接続中の VS Code で「ポート」パネルを開きます。
2. 「ポートの転送」を選び、`8000` を入力します。
3. 転送されたポートの「ローカル アドレスを開く」を選ぶか、開発PCのブラウザで `http://127.0.0.1:8000/` を開きます。
4. TOPの月送り、日付リンク、右側の実データによる出社者一覧を確認します。
5. メニューから「退室点検」を開き、点検者と5項目の結果をタッチして「記録して退室」を操作します。異常あり・未実施では項目に応じた理由を選びます。
6. 保存後TOPのカレンダーに反映された点検状態を確認し、メニューの「点検履歴」から日付を選んで全記録を確認します。
7. 点検者・結果・理由のいずれかを選択して別画面へ移動し、TOPに「点検を再開」が表示されることを確認します。再開時の確認に同じ点検者名が表示され、承認すると入力が戻ります。
8. 点検中に60秒間操作しないとTOPへ戻り、下書きから再開できることを確認します。短縮テストではPlaywright等のページ初期化スクリプトで `window.OFFICE_TERMINAL_IDLE_TIMEOUT_MS = 2000` をページ読込前に設定し、`/menu` などで動作を確認します。
9. 再開した点検者を変更する操作と「下書きを破棄」は、確認でキャンセルすると点検者・入力・下書き・送信キーが残ることを確認します。変更を承認した場合は入力がすべて消え、新しい送信キーと下書き版になります。DB保存に失敗するケースでは入力と下書きが残り、成功すると対応する下書きだけが消えます。

## 点検下書き

下書きはブラウザの `localStorage` に保存し、DBの正式記録とは分離しています。保持範囲は同じブラウザプロファイル内の同じオリジン（接続方式・ホスト名・ポートの組み合わせ）です。別のPC、タブレット、別ブラウザプロファイルには共有されません。同じオリジンの別タブで更新・破棄があった場合は通知し、再読み込みを促します。

点検入力の変更時に下書きを保存し、タイムアウト・ページ再読み込み・ブラウザ再起動後もTOPの「点検を再開」から復元できます。下書きには開始日と更新日時、形式バージョン、送信識別子、点検結果と理由選択を含みます。新形式では備考や自由入力理由を保存しません。旧形式の自由入力を含む下書きは選択肢へ変換せず、説明と確認の後に破棄して新しい点検を開始します。正式記録の日時は従来どおりサーバー保存時刻です。DB保存が成功した場合だけ、対応する送信識別子・版の下書きを削除します。localStorageを利用できない場合は画面に通知し、点検画面の自動復帰を停止します。ブラウザのプライベートモードや保存制限により、保持できない場合があります。

確認時は、入力を少し行ってから再読み込みし、TOPに再開操作が表示されること、入力が復元されること、保存後に再開操作が消えることを確認してください。無操作タイムアウトは点検画面以外でも動作します。時計更新やマウス移動では延長されず、タップ・クリック・キー入力・スクロールで延長されます。

## 画面

- `/` — 日本時間の時計、気象庁の予報による天気欄、SQLite記録を反映した月間カレンダー、実データの出社者一覧
- `/menu` — 退室点検・出社在席・履歴・設定へのメニュー
- `/records` — 点検履歴または出社・在席履歴の選択
- `/inspection` — 点検者選択、5項目の結果と選択理由をSQLite保存
- `/history` — 日付選択と記録日の一覧
- `/history/YYYY-MM-DD` — 選択日の全点検記録
- `/attendance/history` — 出社・在席履歴（日付・社員絞り込み、20件ずつ）
- `/pc/attendance/history` — PC用出社・在席履歴
- `/settings` — バックアップ状態。実行や設定変更、復元はCLIでのみ実施
- `/attendees` — 社員の出社・在席状態変更
- `/pc/attendees` — PC用社員の出社・在席状態変更

点検者の選択は本人認証ではありません。異常あり・未実施の結果には項目ごとの選択理由が必要です。「全員退室」の「確認済み」は、登録上の在席状態で点検者以外の有効社員に「在室」または「離席中」がいない場合に限り、保存時にも在席状態と点検記録を同じDBトランザクション内で確認・保存します。新しい記録の備考は空欄です。過去の記録にある自由入力の理由・備考は履歴で引き続き表示します。新しい点検記録を保存すると、点検者だけを「退勤済み」にし、状態履歴も記録します。記録日時はサーバーで保存した時刻（日本時間）で、実際に扉を出た時刻ではありません。

共用端末の「出社・在席」画面（`/attendees`）とPC用画面（`/pc/attendees`）では、有効な社員を選択して「出社」「離席」「戻り」「退勤」を記録します。どちらも同じ状態遷移と履歴保存処理を使用します。社員選択は本人認証ではなく、他の社員も操作できます。状態と変更履歴はSQLiteへ保存され、アプリ再起動後も保持されます。状態の自動日次リセットはありません。TOPには有効な社員のうち在室・離席中の人だけを表示し、人数もDB状態から集計します。TOP表示中は読取APIから10秒間隔で更新します。取得失敗時は直前の一覧を保持して通知し、成功すれば通常表示へ戻ります。WebSocket等は使用しません。共用端末では無操作60秒でTOPへ戻りますが、PC用画面には無操作TOP復帰はありません。

「履歴」から点検履歴と出社・在席履歴を選択できます。在席履歴は当日・全社員を初期条件とし、登録日時の新しい順に20件ずつ表示します。日付と、過去の記録がある社員（無効社員を含む）で絞り込めます。社員名は操作時点で履歴に保存された値です。日時はサーバーが記録した日本時間であり、実際の入退室時刻とは限りません。点検保存に伴う退勤は「退勤（点検保存）」と表示します。履歴表示は読み取り専用で、状態や履歴を追加しません。

カレンダーは各日の最新記録を表示し、過去の記録は履歴にすべて残します。

## 天気欄

TOP右上の天気欄は、気象庁が公開している予報JSON（`https://www.jma.go.jp/bosai/forecast/data/forecast/<府県予報区コード>.json`）を使います。出典「気象庁」と、加工して表示している旨を画面に表示します。気象庁が公式に仕様を保証したAPIではなく、**提供URLやJSONの形式が予告なく変わる可能性があります**。変わった場合は天気欄だけが「天気情報を取得できません」などになり、点検・在席・履歴・バックアップには影響しません。

- 外部取得はサーバー内の1つの更新タスクだけが行います。起動後に非同期で取得し、30分ごとに更新します（通信タイムアウト10秒、重複実行なし）。画面表示や接続台数で外部アクセスは増えません。画面はアプリ内の `/api/weather` を60秒ごとに読みます（無操作タイマーには影響しません）。
- TOPの表示は3行です。「地域名 アイコン 天気」「最高○℃／最低○℃ 18–24時 ○%」「17:00発表」。長い天気説明はカード内で短い要約にし、全文・出典・加工の表記・気象台名・取得状況は「設定」画面の「天気情報」で確認できます。気温は現在気温ではありません。降水確率は予報の時間帯ごとの値をそのまま表示し、平均は作りません。
- 値は地域コードと日時で対応付けます。日本時間の今日に該当する値がない場合は「—」とし、明日の値は表示しません。気温は、日別の `temps`（0時=最低・9時=最高）と週間予報の `tempsMin`/`tempsMax` を、地点コードと日付で照合して使います（値の大小や配列位置では判定せず、0℃・負の値も扱います）。**夕方（17時発表など）の予報には、その日の最低・最高気温が含まれません**（実データで確認: 17時発表の福岡は翌日0時・9時と週間の翌日以降のみ）。そのため夜は「本日の気温予報なし」と表示します。同じ府県・地点・日付の取得済みの値は、より早い発表のものも保持して表示し、その発表時刻を添えます（地点や日付が違う値は流用しません）。片方だけ取得できた場合は「最高—／最低12℃」のように表示します。
- 取得前は「天気情報を取得中」、取得失敗で保存データがなければ「天気情報を取得できません」です。前回取得データがあれば保持して「更新できていません」と発表日時を表示します。日付をまたいだ古い予報は今日の予報として表示しません。仮の天気へのフォールバックはありません。

### 取得地域の設定

TOML形式の設定ファイルで地域を変更できます。既定の場所は `~/.local/share/office_terminal/weather.toml` で、環境変数 `OFFICE_TERMINAL_WEATHER_CONFIG_PATH` で変更できます。既定の場所にファイルがなければ福岡地方・福岡地点を使います。環境変数で指定したファイルが存在しない場合は設定不備として扱います。設定の変更は**アプリ再起動時に反映**されます（画面からの編集機能はありません）。サンプルは [docs/weather.example.toml](docs/weather.example.toml) です。

```toml
[weather]
display_name = "北九州地方"
office_code = "400000"
weather_area_code = "400020"
temperature_point_code = "82056"
```

| 項目 | 意味 |
|---|---|
| `display_name` | 画面に出す名前**だけ**です。変えても取得地域は変わりません |
| `office_code` | 府県予報区コード（6桁）。取得するJSONの選択（福岡県 `400000`） |
| `weather_area_code` | 天気・降水確率に使う一次細分区域コード（6桁）。福岡地方 `400010` |
| `temperature_point_code` | 最高・最低気温に使う地点コード（5桁）。福岡 `82182` |

コードの調べ方: 気象庁の区域定義 `https://www.jma.go.jp/bosai/common/const/area.json` の `offices` が府県予報区（`children` が一次細分区域）です。地点コードは `https://www.jma.go.jp/bosai/forecast/data/forecast/<office_code>.json` を開き、気温を持つ `timeSeries` の `areas[].area.code`（福岡県なら 福岡 `82182`・八幡 `82056`・飯塚 `82136`・久留米 `82306`）から選びます。URLを直接指定する項目はなく、コードから既定のURLを組み立てます。`weather_area_code` と `temperature_point_code` は、同じ府県予報区のJSONに含まれる必要があります。

設定ファイルの構文・コード形式が不正な場合や、指定コードが応答に含まれない場合（または予報区が存在しない場合）は、別地域へ切り替えず天気欄に「地域設定を確認してください」を表示し、詳細をログに記録します。この場合でも点検・在席機能は通常どおり起動します。開発・テスト用に `OFFICE_TERMINAL_WEATHER_ENABLED=0` で外部取得を止められます（天気欄は「取得できません」表示）。

## 構成とテスト

- `src/office_terminal/main.py` — FastAPIアプリと起動時DB初期化
- `src/office_terminal/web/` — HTTPルート、入力受付、画面への受け渡し
- `src/office_terminal/services/` — 点検入力の業務検証、カレンダー状態生成
- `src/office_terminal/storage/` — SQLiteスキーマと読み書き
- `src/office_terminal/templates/` — Jinja2テンプレート
- `src/office_terminal/static/` — CSSと通常のJavaScript
- `docs/architecture.md` — 責務分担と拡張方針

テストは `PYTEST_DISABLE_PLUGIN_AUTOLOAD=1 uv run pytest` で実行できます（ROSなど、プロジェクト外のpytestプラグイン自動読込を避けます）。顔認証、人感センサー、画面消灯、記録訂正、管理者認証は実装していません。LAN向けの待受と接続先表示は可能ですが、アクセス制御や本人認証はありません。
